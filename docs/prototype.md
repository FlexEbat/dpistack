## A9 — retention EveBox

**Подтверждено по официальной документации** (не живым тестом, но источник актуален и однозначен: `evebox.yaml` config reference + форум support.suricata.io/EveBox GitHub discussions, версия EveBox 0.18.x).

Встроенная настройка, не отдельный cron/скрипт:

```yaml
database:
  type: sqlite
  retention:
    days: 7      # 0 = отключить; для sqlite это дни
    size: "20 GB"  # опционально, максимальный размер БД
```

Работает только для `type: sqlite` (не для Elasticsearch/PostgreSQL — там retention настраивается иначе). Подтверждается логом `evebox::sqlite::retention: Events purged in last 60s: N` при запущенном сервере. **Вывод: A9 закрыт — механизм встроенный, ключ `EVEBOX_RETENTION_DAYS` из раздела 4 мапится на `database.retention.days`.**

## BitTorrent pcap и сигнатура (критерий приёмки 3 слайса 0)

**Файл получен от владельца** (`tests/data/bittorrent.pcap`, 43992 байт, pcap v2.4, 53 пакета, TCP `10.10.10.23:1044` ↔ `10.10.10.22:47309`, метка времени 2007-04-11 — публичный тренировочный сэмпл).

**Проверено реально, вручную, без automation:**

1. Дамп payload подтверждает подлинный BitTorrent handshake в обе стороны — magic-строка `\x13BitTorrent protocol` на смещении 0 в первых двух пакетах потока (`tcpdump -X`).
2. Разбор битового потока по спецификации BT wire protocol (длина-префикс + message id) даёт: **2 handshake, 48 `request` (запрос куска), 7 `have`, 2 `unchoke`, 1 `interested`, 1 `bitfield`**. Это ровно то, что описано как «BitTorrent handshakes and piece requests».
3. Попытка получить официальный набор ET Open (`suricata-update`) — **реально выполнена и реально провалилась**:
   ```
   Fetching https://rules.emergingthreats.net/open/suricata-7.0.3/emerging.rules.tar.gz.
   Error -- Failed to fetch ...: HTTP Error 403: Forbidden
   ```
   Значит группу `emerging-p2p` из ТЗ (раздел «Предметная область») в этом окружении не проверить — сеть до `rules.emergingthreats.net` недоступна. На реальной тестовой машине владельца это должно пройти без проблем.
4. Чтобы не оставлять критерий совсем непроверенным, написал свой тестовый (**не ET, явно помечено**) сигнатурный keyword-rule на magic-байты handshake и прогнал `suricata -r` по настоящему pcap:
   ```
   alert tcp any any -> any any (msg:"TEST BitTorrent handshake (custom, not ET)";
     content:"|13|BitTorrent protocol"; offset:0; depth:20; sid:9000001; rev:1;)
   ```
   Результат — Suricata реально сработала на оба handshake-пакета потока, реальный `eve.json`:
   ```json
   {
     "event_type": "alert",
     "src_ip": "10.10.10.23", "src_port": 1044,
     "dest_ip": "10.10.10.22", "dest_port": 47309,
     "proto": "TCP",
     "alert": {
       "action": "allowed", "gid": 1, "signature_id": 9000001, "rev": 1,
       "signature": "TEST BitTorrent handshake (custom, not ET)",
       "category": "", "severity": 3
     },
     "direction": "to_server",
     "flow": { "pkts_toserver": 1, "pkts_toclient": 0, ... }
   }
   ```
   Это подтверждает: сам движок и реплей `suricata -r` работают корректно на этом pcap и на этом контенте. Но это **не официальная сигнатура ET P2P** и не `ndpi-protocol:BitTorrent` — только доказательство, что механизм детектирования в принципе рабочий.

```

Что нужно: тот же прогон, но с реальной группой правил emerging-p2p (ET Open) и/или со сборкой --enable-ndpi (ndpi-protocol:BitTorrent) — на машине, где рулесет и nDPI реально доступны
```
